# SantiBet Backend (`server/`)

Production-oriented FastAPI backend for SantiBet: a hybrid AMM + order-book prediction
market, with an OpenAI-powered recommendation/market-generation pipeline that's gated
behind an admin review queue, and a double-entry ledger backing all money movement.

**Read this whole file before your first run** - Section 0 below is important.

---

## 0. Honest status of this codebase (read first)

This backend was generated and then manually reviewed/corrected line-by-line, but it
was **written and syntax-checked in a sandboxed environment with no access to PyPI, no
Postgres, and no Redis** - so nothing here has actually been executed end-to-end yet.
Concretely, what *was* done:

- Every `.py` file passes `python -m py_compile` (no syntax errors).
- A custom static checker verified every cross-module `from app.x import y` actually
  resolves to something that exists.
- The Alembic migration was **hand-written** (not autogenerated - no DB was available)
  and then **programmatically cross-checked column-by-column and nullable-flag-by-flag**
  against every SQLAlchemy model, so it should match, but "should match by static
  analysis" is not the same as "ran successfully against Postgres."
- The trading engine, ledger, and resolution logic were manually re-derived and traced
  by hand (see "Known limitations" below for the one real bug found and fixed during
  review, and one accepted narrow edge case).

What this means for you: **budget time for a first-run debugging pass.** The most
likely failure points are minor - a wrong SQLAlchemy/Pydantic keyword arg, an import
that should be a submodule import, a subtle Alembic type mismatch - not fundamental
design problems. Section 3 below gives you the fastest path to surfacing these
(migrate, then hit `/health` and `/docs`, then run the test suite) before you go
looking for a specific bug.

If you hit an error, the fix is almost always local to one file - paste the traceback
into your AI coding agent of choice along with the relevant file and it should be a
quick fix.

## 2. Compliance reminder

You told me this is intended for real money. Real-money event contracts are regulated
in most jurisdictions (in the US, similarly to how Kalshi is CFTC-registered). This
codebase ships in **demo/paper-money mode by default** for exactly this reason -
`PLATFORM_REAL_MONEY_ENABLED=false` in `.env.example`. Don't flip that flag for real
users without a lawyer's sign-off. See the backend planning doc from earlier in this
project for more detail.

## 3. Setup (WSL Ubuntu, Python 3.13)

### 3.1 Place the folder

Unzip so you end up with `<your-project-root>/server/` sitting next to `client/`.

### 3.2 System dependencies

```bash
sudo apt-get update
sudo apt-get install -y postgresql postgresql-contrib redis-server python3.13-venv build-essential libpq-dev

sudo service postgresql start
sudo service redis-server start
```

### 3.3 Database + role

```bash
sudo -u postgres psql <<'SQL'
CREATE ROLE santibet_app WITH LOGIN PASSWORD 'changeme';
CREATE DATABASE santibet_dev OWNER santibet_app;
CREATE DATABASE santibet_test OWNER santibet_app;
SQL
```

(Use a real generated password outside of local dev, and update `.env` to match.)

### 3.4 Python environment

```bash
cd server
python3.13 -m venv .venv
source .venv/bin/activate
pip install -r requirements-dev.txt   # includes requirements.txt + test tooling
```

### 3.5 Configure environment

```bash
cp .env.example .env
# edit .env: at minimum confirm DATABASE_URL / DATABASE_URL_TEST / REDIS_URL match
# step 3.3, and set JWT_SECRET to a long random string.
# OPENAI_API_KEY and STRIPE_* are optional for local/demo-mode dev.
```

### 3.6 Migrate + seed

```bash
alembic upgrade head
python -m scripts.seed
```

`scripts/seed.py` creates the 7 market categories the frontend expects and a dev admin
user (`admin@santibet.dev` / `ChangeMe123!` by default - override via
`SEED_ADMIN_EMAIL` / `SEED_ADMIN_PASSWORD` env vars before seeding, and change the
password immediately in any shared environment).

### 3.7 Run it

```bash
# Terminal 1
uvicorn app.main:app --reload

# Terminal 2 (background jobs: AI generation, signal collection, leaderboard refresh)
celery -A app.core.celery_app worker --loglevel=info

# Terminal 3 (schedules the above on a timer - see app/core/celery_app.py)
celery -A app.core.celery_app beat --loglevel=info
```

Check `http://localhost:8000/health` (should show `database: true, redis: true`) and
`http://localhost:8000/docs` (interactive API docs - the fastest way to try endpoints
without wiring up the frontend yet).

### 3.8 Least-privilege DB grants (recommended, optional for local dev)

```bash
psql "$DATABASE_URL" -f deploy/grants.sql
```

Locks down the ledger and audit log to INSERT-only at the database level. See the
comments in that file for what it does and its limits.

### 3.9 Run the tests

```bash
pytest
```

Tests run against `DATABASE_URL_TEST` (a real Postgres database, not SQLite - the
schema leans on Postgres-specific types). Each test runs inside a rolled-back
transaction, so the test DB stays empty between runs.

### 3.10 Docker Compose alternative

Once `.env` is filled in:

```bash
docker compose up --build
```

Brings up Postgres, Redis, the API (auto-migrates on boot), a Celery worker, and Celery
beat together. `docker-compose.yml` uses its own internal `DATABASE_URL`/`REDIS_URL`
pointing at the `postgres`/`redis` service names - your `.env`'s other values (JWT
secret, OpenAI/Stripe keys, etc.) still apply.

## 4. Connecting the existing frontend

`client/` currently calls only `lib/mock-data.ts` - nothing in the frontend talks to
this backend yet. To wire them together:

1. Set `CORS_ORIGINS=http://localhost:3000` in `.env` (already the default).
2. In the frontend, replace calls into `lib/mock-data.ts` with `fetch` calls to
   `http://localhost:8000/v1/...` matching the endpoints in
   `app/api/v1/routers/*.py` (every response shape matches `client/lib/types.ts`
   field-for-field, so this should mostly be swapping the data source, not
   reshaping data).
3. Store the JWT `accessToken` from `POST /v1/auth/login` / `/v1/auth/signup` in memory
   (e.g. a React context) and attach `Authorization: Bearer <token>` to authenticated
   requests. The refresh token is delivered as an httpOnly cookie automatically.
4. For realtime, connect to `ws://localhost:8000/v1/ws/markets/{slug}` for a market
   ticker, and `GET /v1/ws/ticket` then `ws://localhost:8000/v1/ws/user?ticket=...`
   for authenticated per-user updates (order fills, balance changes).

This wiring pass itself wasn't done here (you asked for the backend); it's the natural
next step.

## 6. Known limitations / next steps

Being upfront about what a "real production launch" would still need on top of this:

- **Narrow race window on resting limit orders**: placing an order checks that you
  have enough free balance/shares (accounting for your *other* open orders), but two
  simultaneous placements by the *same* user could both pass that check before either
  commits. The ledger and position service still catch it at fill time (returning a
  clean 409, never corrupting data), but in that rare case a fill could fail. Closing
  this fully means adding a persisted `reserved_cash` / `reserved_shares` counter with
  row-level locking instead of the current query-time check.
- **`volume_24h` is eventually-consistent**: updated incrementally on every trade, then
  corrected precisely every 5 minutes by `refresh_market_stats_task`. Fine for a
  ticker, not for anything billing-sensitive.
- **`Transaction.balance_after` in `GET /wallet/transactions` is the current balance**,
  not a true historical point-in-time balance (the ledger doesn't store a running
  total by design - see `wallet_service.py`). Computing an exact historical running
  balance would mean replaying `ledger_entries` in order, which isn't wired up yet.
- **AI signal providers** (`app/services/ai/signal_collector.py`) are implemented
  against CoinGecko/FRED/a generic news API pattern - confirm those specific API
  contracts still match at build time (external APIs change) and add your own API
  keys.
- **OpenAI model name**: `OPENAI_MODEL` in `.env.example` is a reasonable default but
  check OpenAI's current docs for what they recommend for structured JSON output at
  the time you deploy - model names/availability change.
- **Table-owner caveat on `deploy/grants.sql`**: see the comments in that file - full
  isolation needs a separate migration-owner role vs. app-runtime role, which isn't
  set up here.
- Rate limiting, 2FA (TOTP scaffolding exists on the `users.totp_secret` column but
  isn't wired into login yet), and structured observability (Prometheus/Sentry) are
  either partial or noted-but-not-wired - see the original backend plan doc for the
  intended full scope (Phase 10/11) if you want to take this further.
